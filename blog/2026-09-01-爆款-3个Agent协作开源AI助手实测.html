多 Agent 协作到底解决什么：四种编排模式与各自的天花板

「3 个 Agent 协作」「30 天记忆不丢失」这类结论依赖具体产品与测试条件，这里不作为依据。给的是多 Agent 的编排模式与判断方法，换一个框架依然成立。

先说一个容易误解的点：多 Agent 不会让模型变聪明。同一个模型，拆成三个角色互相说话，单步能力一点没变。

它真正带来的是三件事：上下文隔离、职责约束、可并行的分工。反过来说，如果你的问题不需要这三样，多 Agent 只会让你多付几倍的钱。

四种常见的编排模式

模式怎么运转什么时候值得用
串行流水线A 的输出喂给 B，B 给 C任务本身天然分段，且每段标准不同
主管-工人一个调度者拆任务，分给多个执行者子任务可并行，数量不定
评审 / 辩论一个产出，另一个挑错，循环若干轮有明确的对错标准，且错误代价高
交接式按条件把对话转给不同角色客服、分流、多技能路由

四种模式的天花板各不相同：

  • 串行流水线：错误会累积，第一段错一点，后面全歪
  • 主管-工人：调度者是瓶颈，它拆错任务，工人再强也没用
  • 评审 / 辩论：收益递减很快，通常两轮之后就没有新增价值
  • 交接式：交接处丢信息，上下文压缩是最大的坑

三个必须自己跑的对照实验

下面三个实验，每个都能在一个下午做完。做完你就知道该不该上多 Agent。

实验一 · 单 Agent 基线

先用一个 Agent + 一份完整提示词把任务做一遍，记录：完成率、产出可用率、总花费、总耗时。

这个基线非常重要。我见过太多方案，多 Agent 版本比单 Agent 更差——但因为没人跑过基线，所以没人知道。

实验二 · 错误放大测试

在中间某个环节人为注入一个错误输出，看系统会不会把它放大。

好的编排会把错误挡在下一道关卡（比如校验环节），差的编排会让错误扩散成整份产出都不可用。这个测试比测「成功率」更能看出设计的健壮性。

实验三 · 轮数收益曲线

把评审轮数从 1 加到 2 加到 3，记录质量与成本。

多数情况下，第二轮有明显提升，第三轮开始只有成本上升。找到那个拐点，就设成你的固定轮数上限。

四个最常见的失败模式

失败模式表现怎么防
职责重叠两个 Agent 干同一件事，产出还打架给每个角色写清「不负责什么」
交接丢信息下游不知道上游的约束条件交接时带结构化字段，不要只带自然语言摘要
死循环两个 Agent 互相要求对方重做设轮数上限 + 明确的终止条件
成本爆炸轮数 × 上下文，账单翻几倍限制每次传递的上下文长度，日志里记花费

第二条最隐蔽。自然语言摘要会丢约束——上游说「金额必须保留两位小数」，摘要之后这句话就没了。所以交接要传结构化字段，不是传一段话。

关于「长期记忆」这件事

很多产品把「记住你」当卖点。实际实现通常是三层，稳定性差别很大：

层怎么实现可靠性
会话内上下文就是窗口里的内容高，但会随长度衰减
外部检索存起来，用时按相似度捞回来中，取决于检索质量
结构化状态像数据库一样存字段高，但需要设计 schema

关键结论：记忆的难点不是「记住更多」，是「该忘的忘掉」。把所有历史都塞进去，结果就是关键的约束被淹没。

可用的做法：把「事实」和「当前任务状态」分开存。事实长期留，任务状态用完即弃。

选型判断表

拿你自己的任务对一遍，命中两行以上再考虑多 Agent：

你的情况是否适合
任务能自然分段，每段标准不同适合串行流水线
有大量可并行的子任务适合主管-工人
有明确对错标准且错误代价高适合评审模式
单 Agent 已经做得不错，只是慢不适合，多 Agent 会更慢
问题在于模型不知道你的数据不适合，该上检索
问题在于输出格式不稳不适合，该改提示与校验

后三行是现实中最常见的情况。把数据问题、格式问题当成「需要更强的智能体」来解决，是最贵的一种弯路。

小结

多 Agent 是一个工程结构，不是能力升级。它擅长把复杂任务拆开、把上下文隔开、把错误挡住；它不擅长让模型更懂你的业务。先跑通单 Agent 基线，再决定要不要加人。
