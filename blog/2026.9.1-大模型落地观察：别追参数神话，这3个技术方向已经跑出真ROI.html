大模型落地观察：三个真在产生价值的技术方向

「已跑出真 ROI」的百分比没有可追溯来源，这里不引用。给的是三个方向各自解决了什么问题、成本结构长什么样、什么场景不适合用。划不划算，按自己的调用量与人力成本代入算。

参数规模早就不是判断标准了。一个 7B 的模型在特定任务上稳定超过通用旗舰，这种事现在很常见——因为窄任务的容错空间大，通用任务没有。下面三个方向的共同点是：都不追求通用，只解决一段明确的流程。

方向一 · 端侧小模型推理

端侧的价值不在"便宜"，在数据不出设备和零延迟这两件事上。凡是涉及个人隐私（健康、财务、聊天记录）或要求即时响应（离线翻译、本地问答）的场景，云端方案再便宜也不合适。

代价要说清楚：

  • 参数规模受内存和功耗约束，通常 8B 以下，复杂推理明显不如云端旗舰
  • 量化之后精度有损，同一句话换个说法结果可能不同
  • 升级意味着重新分发模型文件，不像云端那样静默生效

所以判断标准是：这个任务错一次的代价，能不能接受。离线翻译错一个词能接受，合同条款解读错一句不能。

方向二 · 多模态 RAG

RAG 的老问题一直是"搜不准、答不对"。引入多模态之后，真正改善的不是"能搜图了"，而是检索时能用图里的信息定位文字——比如一张产品图，图上有型号标签，检索可以直接命中这个标签。

但这一层有一个绕不过去的成本：视觉 token 比文本 token 贵得多。同一张发票，按文本抽取只要几百 token，按图像输入可能是数千 token。所以多模态 RAG 只适合"文本里确实拿不到的信息"，不适合拿来替代 OCR。

  • 适合：图纸、表格截图、带标注的产品图、手写批注
  • 不适合：本来就有电子文本的 PDF（直接抽文本便宜一个数量级）
  • 必须做：给每个回答带原文位置，否则用户无法验证，等于没做

方向三 · Agent 工作流

"全自动打工"现在做不到，别信。能落地的是半自动：把一段流程拆成若干步，机器做可判定的步，人做需要拿主意的步，中间留人工确认点。

成本结构上，Agent 最大的坑是上下文反复回传：每一轮都要把历史带上，所以缓存命中率比模型单价更决定账单。DeepSeek 的缓存命中输入低至 0.006 美元每百万 tokens，同样的多轮循环，账单能比不用缓存差一个数量级。

  • 能自动：格式整理、字段抽取、状态更新、按规则路由
  • 不能自动：优先级判断、例外审批、对外承诺、涉及金额或法律的决策
  • 必须留：人工确认点，以及出错时的回滚路径

三条给从业者的判断线

  • 先算人的成本，再算 token 成本。token 便宜到今天这个程度，决定方案能不能上的从来是人力的重构成本，不是模型账单。
  • 能写死规则的地方不要交给模型。规则正确率 100%，模型永远不是，而且规则的行为可预测、可审计。
  • 给每个结论留出处。不管是检索到的原文还是调用的接口返回值，用户能点开验证的方案，才可能被长期用下去。
