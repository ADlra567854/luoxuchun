## 0. 一句话问题

**关键结论：**

1. **线上包不是「旧包」——它就是今天 00:00 那一批。** md5 比对：线上 `index.html` / `api/health` / `legacy-redirects.mjs` 与本地 `deploy/` **三者 md5 全部一致**。
2. **今天 00:00 的发布是按「静态形态」跑的**，所以后端没启动。`deploy/` 里的 `server.mjs` 和 `package.json` 是 10:50 才被补进去的（`prepare-deploy.mjs --with-server` 路径），**这批从未发布**。
3. **线上 `server.mjs` md5 与本地一致**（`84b76b00...`），说明文件同步上去了，**但进程没被拉起** —— 平台把它当静态站托管了。

## 3. 处置方案

### 方案 A（推荐）：以 Node 常驻形态重新发布 `deploy/`

**做什么**：把 `deploy/` 按 Node 应用发布（`language: node`，`startCmd: node server.mjs`），让 `server.mjs` 真正在沙箱里跑起来。

**一次性解决三件事**：
- `server.mjs` 的 `DENY_FILE` 生效 → `/ai.config.json` 变 **404**，明文 key 不再暴露
- `/api/health` 返回完整 `caps` → 校验通过
- `legacy-redirects.mjs` 被 `server.mjs` import → 5 条旧路径恢复 **301**

**前提**：`deploy/server.mjs` 已确认监听 `PORT` 且绑 `0.0.0.0`（第 563 行），符合平台单端口要求。

**注意**：`deploy/` 当前 290 MB / 2376 文件，含大体积素材。发布耗时可能较长。

### 方案 B（保守）：维持静态形态，只做密钥止血

若老罗决定继续用纯静态托管（如为了省沙箱资源），则只需保证线上 `ai.config.json` 被无密钥内容覆盖：

- 现状 `deploy/ai.config.json` 已经是无密钥版，但**上次发布没同步上**
- 需要用发布工具**重新发布一次**，让增量同步把这份文件推上去
- 代价：`caps` 永远为空、5 条旧路径永远不是 301 → **巡检项三、六持续不达标**

**推荐 A。** 纯静态形态下 `caps` 与 301 这两项在架构上就无法满足，而它们是巡检清单的硬性项。

### 方案 C（长期）：让 `prepare-deploy.mjs` 默认带后端

改回默认 `--with-server`，避免每次发布都要手工加参数。当前是「默认静态、显式带后端」，但实际发布流程没有跟进这个参数 —— 这是流程缺口，不是代码 bug。

**建议**：无论选 A 还是 B，都应补一条发布脚本，把「构建 → 预检 → 发布 → 复测」串成一条命令，杜绝「本地改了没发」或「发错形态」。

## 4. 密钥轮换（独立于形态，**最高优先级**）

**无论选哪个方案，都建议老罗轮换讯飞 key。**

理由：明文 key `ak-6YT****（已脱敏，原值见 .env）` 已在公网可读状态下存在了至少 11 天（10-29 起）。历史上出现过**两次**暴露窗口（11-11 巡检也发现过一次，同样是 200 明文）。

- 本地 `.env` 是唯一持有该 key 的地方（另有 `.tmp/cors.mjs`、`.tmp/online-aiconf.json` 两个临时文件残留 —— 已列入清理）
- 轮换后同步更新 `.env`，旧 key 立即失效
- 这是**唯一能真正关闭暴露窗口**的动作，形态调整只是让 404 规则生效
