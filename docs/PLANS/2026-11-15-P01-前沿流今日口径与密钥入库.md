## 问题 1（高）：`feed.json` 的 `updated` 落后真实最新条目 4 天 → 「近 7 天」窗口失真

### 现象

| 指标 | 值 |
|---|---|
| `data/feed.json` → `updated` | `2026-11-10` |
| `data/feed.json` → items 里最大 `d` | `2026-11-14`（**差 4 天**）|
| 首页「近 7 天」区间文案 | `2026-11-03 — 2026-11-10` |
| 首页实际渲染的卡片日期 | `11-14 / 11-13 / 11-13 / 11-10 / 11-10 / 11-10` |
| `/feed/` 页「近 7 天」计数 | **17 条**（实际跨度 **11 天**）|
| 真实 7 天窗口应有的条数 | 14 条（多算 **3** 条）|

### 根因

`scripts/gen-feed.py` 用 `data['updated']` 作为「近 7 天」窗口的**右端锚点**：

```python
# scripts/gen-feed.py:195
today = parse(data['updated'])
start = today - timedelta(days=7)
items = [... if parse(i['d']) >= start][:n]
```

而 `updated` 字段**只由人工/外部流程写入 `data/feed.json` 时才会 bump**。今天流水线确实往 `items` 里追加了 3 条（`llama.cpp 1.0`、`DeepSeek 全家桶 API`、`流程工业智能工厂国标`，日期 11-13 / 11-14），**但 `updated` 没跟着 bump**，仍停在 `2026-11-10`。

于是：
- 窗口右端 = 11-10，比真实最新条目（11-14）早 4 天
- 首页把 11-13 / 11-14 的卡片摆进「近 7 天」，但区间文案只写到 11-10 → **文案与卡片自相矛盾**
- `/feed/` 的「近 7 天 17」实际含了 11 天前的条目

### 关键澄清（避免误判）

`scripts/gen-feed.py` **不造数据**（文件头注释明写「只做渲染，不造数据。要加条目改 data/feed.json」）。所以这**不是** gen-feed 的 bug，而是**数据真源缺一个自动 bump 步骤**。

### 建议方案

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 在 `scripts/daily-update.mjs` 的 changelog 写入段（约 199–240 行）**之前**加一步：读 `data/feed.json`，若 `max(items[].d) > updated`，则把 `updated` 更新为 `max(items[].d)` 并写回 | 改 1 处，约 8 行；让「近 7 天」右端锚点自动跟随真实最新条目 |
| B | 在 `gen-feed.py` 内部改用 `max(items[].d)` 作为锚点，不再读 `updated` | 渲染层自洽，但 `feed.updated` 字段本身继续撒谎（外部消费方仍会读到错值）|
| C | 要求每次追加条目的人手动 bump `updated` | 零代码改动，但依赖人 —— 今天的失真就是这么来的，不可靠 |

**建议 A + B 组合**：A 保证字段真，B 保证渲染层即使字段没跟上也不出错。

## 问题 2（高）：`ai.config.json` 明文密钥被 git 跟踪，且远端仓库为 public

### 现象

| 检查项 | 结果 |
|---|---|
| `git ls-files --error-unmatch ai.config.json` | **命中**（已被 git 跟踪）|
| `git show HEAD:ai.config.json` | 含 35 字符明文 key（`ak-6YT…`）|
| 提交 | `88ae5ed checkpoint: before domain cleanup` |

| 该仓库可见性 | **`private: false` / `visibility: public`** ⚠️ |
| `origin/main` 是否已含该文件 | 否（`ai.config.json` 在 `origin/main` 上不存在）|
| 提交 `88ae5ed` 是否已推到远端 | **否**（GitHub API 查该 SHA → `No commit found`，仅存在于本地分支 `feature/home-brand-path`）|

### 风险分级

- **线上站点**：✅ 安全。`/ai.config.json` 返回 **404**（`server.mjs` 的 `DENY_FILE` 规则生效，已实测本地 8098 与线上均 404）
- **公网仓库**：⚠️ **高危但尚未爆**。密钥已进入本地 git 历史；当前只差「把 `feature/home-brand-path` 推到 GitHub」这一步就会公开。仓库是 public，任何人 clone 即可拿到 key
- **本地 `deploy/ai.config.json`**：也含明文 key，但 `DENY_FILE` 挡住 HTTP 读取，线上 404

### 建议处置（按优先级）

1. **【最高】轮换讯飞 key** —— 密钥已在本地 git 历史中，且本轮 `deploy/ai.config.json` 也是明文。既然它「已经存在过」，按「已泄露」处理最稳妥
2. **立即从索引移除并加忽略**（不动历史）：
   ```bash
   git rm --cached ai.config.json
   echo "ai.config.json" >> .gitignore
   ```
3. **本地历史净化**：用 `git filter-repo --path ai.config.json --invert-paths`（或 BFG）清掉历史中的该文件
4. **远端防护**：确认 `feature/home-brand-path` 在净化完成前**不要** push；仓库可先转 private
5. **构建侧加固**：`scripts/prepare-deploy.mjs` 应保证 `deploy/ai.config.json` 落的是**无密钥占位**（服务端走 `SPARK_KEY` 环境变量），而不是把真 key 打进发布包

> ⚠️ 注意：11-13 那轮已知「`prepare-deploy` 静态分支会把 `deploy/ai.config.json` 写成无密钥占位，反向覆盖根目录真源」的坑（见 `.workbuddy/memory/2026-11-15.md`）。修第 5 条时**不要**再引入反向覆盖 —— 占位写入必须限制在 `deploy/` 目录内。

## 问题 3（中）：`changelog.json` 与 `feed.json` 逐日计数有 2 处 MISMATCH

### 实测（11-15）

```
2026-11-15  changelog.feed=0  feed.json 实际=0   OK
2026-11-13  changelog.feed=0  feed.json 实际=2   MISMATCH   ← 本轮流水线追加的 2 条回填到 11-13
2026-11-10  changelog.feed=4  feed.json 实际=4   OK
2026-11-09  changelog.feed=5  feed.json 实际=5   OK
2026-11-04  changelog.feed=1  feed.json 实际=1   OK
2026-11-02  changelog.feed=5  feed.json 实际=6   MISMATCH   ← 历史遗留，note 少列了「深度原理开放 753B」
2026-11-01  changelog.feed=1  feed.json 实际=1   OK
```

另：`feed.json` 有 **30 个日期**在 `changelog.json` 里完全没有条目（10-28、10-27、10-26 … 一直到 09-17），因为 `daily-update.mjs` 只在「流水线当天跑过」的日子写 changelog。

### 说明

- **本轮（11-15）不需要改**：`entries[0].date = 2026-11-15` ✅ 是今天；`feed: 0` 与 `feed.json` 今日条数 `0` ✅ 一致。按巡检指令「不一致就修」，**今日这一条是一致的，故未改动 `data/changelog.json`**
- **11-13 的 MISMATCH 是今天流水线造成的**：今天往 `items` 里追加了 2 条 `d=2026-11-13` 的条目，但 11-13 那条 changelog 是当天跑的时候写的（当时确实是 0 条）。修法：在 `daily-update.mjs` 写 changelog 时，不只统计「今天」，还应**回溯修正最近 N 天的计数**
- **11-02 的 MISMATCH 是历史遗留**：note 只列了 4 个标题（代码里 `titles` 硬取 `slice(0, 4)`），但 `feed` 字段记的是 `todayFeed` 全量 —— 说明当时的计数与 note 生成逻辑就已经脱节

### 建议

1. `daily-update.mjs` 写 changelog 时，**回填最近 7 天**的 `feed` 计数（取 `feed.json` 实际值），避免追加回填条目造成历史漂移
2. `note` 的标题列表与 `feed` 计数应同源：要么都取全量，要么 note 明写「等 N 条」

## 问题 4（中）：`.is-today` 仍按「最新批次」而非「当天」判定

沿用 `docs/PLANS/2026-11-12-P02-分享链接sharecode与今日标签口径.md` 的问题 2，本轮仍未修。

- 文案写「今日新增 1 条」—— 指的是 11-14 那条，不是今天
