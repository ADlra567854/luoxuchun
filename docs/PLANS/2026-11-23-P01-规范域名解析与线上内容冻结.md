## 〇、摘要：一句话讲清三条硬伤的关系

```
根因（上游·域名层）
  ccoworkbaiju.cn 在 DNSPod 托管、NS 正常，但【无 A 记录】→ 域名解析失败
        │
        ├─→ 表征①：站点没有可用的根入口
        │      → 规范入口 ccoworkbaiju.cn 全站 5 路径 ENOTFOUND
        │      → 退而访问 GitHub Pages 项目页子路径 /luoxuchun/
        │           → 全站 552 个 HTML、12236 处根绝对路径引用失效
        │           → /about/changelog.html 渲染 0 条记录（"更新记录读取失败"）
        │
        └─→ 诱因：WorkBuddy 应用（ff7990…workbuddy.host）成了唯一可访问入口
               但它【自 11-20 起再未发布】→ 线上内容冻结三天

独立问题（发布链路层）
  发布包形态 ↔ 巡检 caps 契约互斥
    静态包（当前 deploy/）：caps = {} / api/chat 404 / ai.config.json 200
    Node 常驻（线上现状）：caps = {chat:true,proxy:true,…} / api/chat 400 / ai.config.json 404
    → 重发静态包 = 主动回退并违反巡检契约；不重发 = 内容继续陈旧
```

**结论先说**：三条硬伤里，**①是根、②是果、③是独立决策**。
优先修 ①（补 A 记录 + 落 CNAME）—— 一条 DNS 记录 + 一个 CNAME 文件就能让 ① 和表征一起消失，
且顺带解决 ② 的"线上内容陈旧"问题（因为规范域名会指向 gh-pages，而 gh-pages 今天已经推了 11-23 的内容）。

## 一、【高】规范域名 ccoworkbaiju.cn 解析失败

### 1.1 实测证据

| 检查 | 结果 |
|---|---|
| `socket.gethostbyname('ccoworkbaiju.cn')` | `gaierror [Errno 11001] getaddrinfo failed` |
| `socket.gethostbyname('www.ccoworkbaiju.cn')` | 同上 |
| `nslookup ccoworkbaiju.cn 8.8.8.8` | `NS: cabbage.dnspod.net / partridge.dnspod.net`，**无 A 记录** |
| `curl /` | `URLError: Tunnel connection failed: 502`（本机代理无法出网，非站点结论） |
| 今日 `data/runtime-probe.json` | 该域名 5 个路径全部 `ENOTFOUND`（站点自身脚本独立留痕，与本次结论一致） |

`site.config.json` 已把 `siteBase` 声明为 ``，
并把 `ff7990…workbuddy.host` / `已下线的旧发布域workbuddy.link` / `已下线的旧发布域workbuddy.link` 列入 `retiredBases`。
**即：站点唯一的正式入口是死的，而被标记为"已退役"的旧应用反而是当前唯一能打开的入口。**

### 1.2 连带表征：gh-pages 子路径 404

`ADlra567854/luoxuchun` 是 **GitHub Pages 项目页**，站点实际挂载在子路径
`https://adlra567854.github.io/luoxuchun/`（用户根 `https://adlra567854.github.io/` 返回 GitHub 官方 "Site not found" 404）。

但全站 HTML 大量使用**根绝对路径**：

```
发布目录统计：552 个 HTML 文件、12236 处 (href|src)="/..." 根绝对路径引用
```

子路径下这些引用会解析到 `https://adlra567854.github.io/…` → 全部 404。实测：

| 页面 | 失败资源数 | 关键影响 |
|---|---|---|
| `/` | 12 | `site-nav.css` / `float-dock.css` / `feed.css` / `baiju-assistant.js` / `site-nav.js` / `home-fold.js` / `data/ai-projects.json` / `stats.js` / `data/wechat-pick.json` / `search.js` / `data/content-cite.json` / `api/health` |
| `/about/changelog.html` | 14 | **`fetch('/data/changelog.json')` 404 → 页面显示「更新记录读取失败（HTTP 404）」，`.cl-day` = 0，console 错误 25** |

首页「近 7 天」条**正常**（`index.html` 用相对路径 `fetch('./data/daily-brief.json')`），
这正是容易误判为"站点正常"的原因 —— 数据能读不代表页面能用。

### 1.3 建议方案（推荐 A）

**方案 A（推荐）：把规范域名正确绑到 GitHub Pages —— 一次性根治**

1. DNSPod 加 A 记录：`ccoworkbaiju.cn` → GitHub Pages 官方 IP
   `185.199.108.153` / `185.199.109.153` / `185.199.110.153` / `185.199.111.153`
   （建议 TTL 600；配 `www` 同值）
2. 仓库根新增 `CNAME` 文件，内容单行 `ccoworkbaiju.cn`
   （仓库设置 → Pages → Custom domain 填 `ccoworkbaiju.cn`，勾选 Enforce HTTPS；
   GitHub 会在 `gh-pages` 分支自动生成/维护 CNAME）
3. `scripts/sync-ghpages.mjs` 的 `KEEP` 集合**已含 `CNAME`**（第 56 行）→ 同步时不会被清理，**无需改代码**
4. 验证：`/` 可打开 → 所有 `/…` 绝对路径在域名根成立 → ①与表征一并消失

**方案 B：把全站根绝对路径改成相对路径**

- 代价：12236 处引用、552 个文件，且 `fetch('/data/…')` 属于 JS 动态拼接，改动面极大、易漏
- 收益：只依赖 GitHub Pages 子路径，不依赖域名
- 评价：**不推荐**，治标不治本，且长期维护成本高

**方案 C：暂用 `https://adlra567854.github.io/luoxuchun/` 作为正式入口**

- 需要把 `site.config.json` 的 `siteBase` 改成子路径，并接受链接体系仍要改（否则全站导航仍错）
- 评价：也不推荐，只是把问题从"域名"挪到"路径"

## 三、【高】发布包形态 ↔ 巡检 caps 契约互斥

### 3.1 两种形态实测对照

| 判据 | 静态包（当前 `deploy/`） | Node 常驻（线上现状） | 巡检期望 |
|---|---|---|---|
| `/api/health` | `{"status":"static","backend":false,"caps":{}}` | `{"ok":true,"ai":true,"model":"spark-x2.6","caps":{chat:true,proxy:true,auth:false,comments:false,notify:false}}` | **Node 常驻** |
| `POST /api/chat` | 404 | **400** | 非 404（证明后端在跑） |
| `/ai.config.json` | **200**（无 DENY_FILE 兜底） | **404** | **404** |
| `/toolbox/skills.html` | 404 | 301 → `/toolbox/index.html` | 301 |
| `/website/*` 旧路径 | 200（文件直出） | 301（`legacy-redirects.mjs`） | 301 |
| `deploy/server.mjs` | 墓碑占位（97 B） | 真实 25 KB | — |
| `deploy/package.json` | 无 `scripts.start` | 有 `start: node server.mjs` | — |

`prepare-deploy.mjs` 走静态分支时会写墓碑 `server.mjs` / `package.json` 与无密钥 `ai.config.json` 占位；
`--with-server` 分支则会把**根 `ai.config.json`（含 35 字符明文 key）与真实 `server.mjs` 一起复制进包**。
11-15 契约校准（`daily-update.mjs` 注释明写）已把默认固定为**静态 + 纯 BYOK**，
理由正是"`--with-server` 会同时击穿『发布包零明文密钥』与『deploy/server.mjs <500 B』两条硬约束"。

### 3.2 这意味着

- **重发静态包 → 线上 caps 变 `{}`、`/api/chat` 变 404、`/ai.config.json` 变 200** → 直接违反巡检契约，且扩大密钥面
- **改用 `--with-server` → 发布包内重新出现明文 key** → 击穿 11-19/11-20 轮持续上报的 P0 级安全项

**两条路都会让当前"10/10 健康"变成不健康。所以本轮选择：不动、不发、只报告。**

### 3.3 建议（按优先级）

**方案 A（推荐）：把"正式站点"与"WorkBuddy 应用"解耦**

- 正式站点 = GitHub Pages + `ccoworkbaiju.cn`（第一题），跑**纯静态 + 纯 BYOK** —— 与 11-15 契约一致，零明文密钥
- WorkBuddy 应用 = 保留为 **Node 常驻**（可继续带 `/api/chat` 代理能力），但**改用 `--with-server` 且从环境变量读密钥**（`SPARK_KEY`），发布包内 `ai.config.json` 只留空壳
- 前提：确认 CloudStudio / WorkBuddy 沙箱能否注入环境变量。**这一条本轮无法单方面验证，需老罗确认。**

**方案 B：把巡检契约改成接受静态形态**

- 即 caps 期望值按形态区分（Node 常驻 → 满值；静态 → `{}`），`/api/chat` 404 也算正常
- 代价：站点失去 AI 代理能力，前端全部走浏览器直连 BYOK
- 评价：与 11-15 契约一致，但等于**主动放弃服务端能力**，需老罗拍板

**方案 C：现状冻结**

- 规范域名修好后，用户走 gh-pages，WorkBuddy 应用只当"备用/演示"
- 代价：WorkBuddy 应用与规范站点内容不同步（应用停在 11-20），巡检需把主判据切到新渠道

**无论选哪个方案，都建议补一条硬闸门**（这是 11-19 起就建议、至今未做的）：

> `prepare-deploy.mjs` 在产出后加自检断言：
> 若产物形态为静态（`server.mjs` 是墓碑），则断言 `api/health` 桩存在且 `ai.config.json` 的 `key` 为空；
> 若产物形态为 Node 常驻（`--with-server`），则断言包内 `ai.config.json` 的 `key` **为空**（密钥只能来自环境变量），
> 命中明文即**失败退出、不产出包**。
> 断言不通过 → 直接中止发布，避免"发出去才发现退化"。
