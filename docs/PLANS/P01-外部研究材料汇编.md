## 材料一：品牌 logo 的版权边界 —— 为什么本站用「品牌色 + 缩写字母标」而不是真 logo

**来源**：Lucide 官方《品牌 Logo 声明》
**原文链接**：http://lucide.dev/brand-logo-statement
**中文版**：https://lucide.zhcndoc.com/brand-logo-statement

### 结论摘要

Lucide 从不收录品牌 logo，且明确表示未来也不会收录。三条理由：

1. **法律限制**：多数品牌 logo 受商标或版权保护，对使用方式（颜色、间距、比例）有严格规定，不允许修改。收录进来等于把使用者与图标库一起置于侵权风险中。Material Design Icons 与 Feather Icons 早年就因为同样原因弃用了品牌图标。
2. **设计一致性**：品牌 logo 与象形图标（pictogram）是两类根本不同的图形。硬塞进同一套 24×24 描边网格，必然导致一部分图标「格格不入」，破坏整套视觉语言的统一。
3. **维护负担**：logo 会变，图标库维护者需要逐个跟进，且每次请求都要重新做一次法务判断。

### 官方推荐替代方案

- **Simple Icons**：专门做品牌标志的集合，SVG 格式统一，同样是 24×24 viewBox，法律风险相对更低。
- **各公司官方品牌资源页**：多数大厂都提供官方 SVG 下载。

### 本站的做法与依据

白驹 ccowork 的厂商墙原本用「中文首字 + 随机渐变」（深、阿、字…）当图标。这既不是 logo 也认不出公司，属于自欺欺人的假图标。

本轮改为 **品牌色实底 + 英文缩写字母标**（DS / QW / BY…），依据有三：

1. 抓取 43 家真实 logo 不可行（逐一维护 + 商标授权问题）
2. 字母标 + 品牌色是业界通行的合规做法，与 Simple Icons 同一思路
3. 与全站 24×24 描边式图标规范不冲突（方块圆角 + 白色粗体字）

补充佐证：Lucide 1.0 官方发布说明中提到移除品牌图标使 React 包体积减少 32.3%（11.4MB → 约 1MB gzip），核心驱动同样是「法律风险 + 一致性 + 维护成本」三重考量。
来源：https://www.otf-kit.dev/blog/lucide-icons

## 材料二：301 重定向迁移的标准做法

**来源**：FastRedir《301重定向对 SEO 有什么影响? 网站改版、旧链接迁移与权重承接的实操指南》
**原文链接**：https://www.fastredir.cn/blog/301-redirect-seo-migration-guide

### 五步执行顺序（本轮 P01 步骤 4 依此设计）

1. **先拉旧 URL 清单，再做映射表** —— 每个旧 URL 明确写清对应的新 URL
2. **先让新页面可访问，再启用迁移规则** —— 不能把老流量导进半成品页面
3. **按页面关系做 301，不按目录粗暴替换** —— 内容合并/拆分/重命名的重点页面单独处理
4. **同步更新站内链接、canonical 与 sitemap** —— 这一步直接决定搜索引擎多久把新地址当主版本
5. **抽样测试再监控** —— 盯 404 日志、错误跳转、循环跳转、不必要的双跳三跳

### 状态码分工

| 状态码 | 适用场景 |
|---|---|
| 301 | 长期稳定迁移，以后都用新地址 |
| 302 | 临时切换、A/B 测试、活动页试跑 |
| 308 | 长期迁移且要求严格保持请求方法 |

### 本轮落地对照

| 标准步骤 | 本站实现 |
|---|---|
| 拉旧 URL 清单 | `legacy-redirects.mjs` 的 `LEGACY_MAP`（27 条显式映射） |
| 新页面先可访问 | 10 个薄壳落地页由 `gen-legacy-shells.py` 先生成，映射才启用 |
| 按关系做 301 | 每条映射按语义对应（如 skill-hub → /toolbox/skills.html） |
| 同步站内链接与 sitemap | `site-nav.js` 9 个入口改指新版；`gen-seo.mjs` 排除旧 URL、补入虚拟路径 |
| 抽样测试 | 启动自检：目标不存在则拒绝启动；回归测 5 条旧路径的 301 + Location |

## 材料三：301 重定向的常见错误（用于自检清单）

**来源**：How To Learn SEO《301 Redirects for SEO: A Complete Beginner's Guide》
**原文链接**：https://howtolearnseo.com/?p=399

### 必须避免的六类错误

1. **重定向链**（A → B → C）：改第一条规则直接指向最终目标
2. **重定向循环**（A → B → A）：改完逻辑后要测各种变体
3. **无关页面全跳首页**：Google 可能当 soft 404
4. **所有 404 自动跳转**：只重定向已知的旧 URL
5. **临时场景用 301**：该回來的用 302
6. **站内链接仍指旧地址**：每多一跳都是自己给自己加摩擦

### 关键实践

- **sitemap 只列最终 URL**，不列会立刻跳转的旧地址
- 内部链接应直接指向新地址，不靠重定向跳转
- 至少保留重定向一年（搜索引擎需要时间重新抓取与转移权重）
- 目标页应带自引用 canonical

### 本轮对应实现

- ✅ sitemap 排除 27 条旧映射 + 补入 157 条虚拟路径
- ✅ 站内导航 9 个入口全部改指新版（`site-nav.js` 中 `website/` 引用仅剩 2 处注释与 1 处域判定逻辑，均为必要保留）
- ✅ 映射表目标存在性自检（`verifyTargets()`），有失效目标拒绝启动
- ✅ 无重定向链：旧路径 → 新路径为单跳（实测 `curl -I` 验证）

## 材料四：SEO Image 的 301 与 canonical 教程（补充校验清单）

**来源**：SEO Image《301 Redirects & Canonical URL Tutorial》
**原文链接**：https://seoimage.com/301-redirects-canonical-url-tutorial

### 理想状态验证法

```
Old URL:  301 Moved Permanently
New URL:  200 OK
```

必须同时满足：
- 第一个响应是 301 而不是 302
- 目标地址是预期的那一个
- 没有不必要的重定向链
- 最终页返回 200
- HTTP/HTTPS、www/非 www 变体行为一致
- 保留了正确的路径与查询串

### curl 验证命令

```bash
# 只看第一个响应
curl -I https://www.example.com/old-page/
# 跟随完整跳转路径
curl -I -L https://www.example.com/old-page/
```

### 本轮实测记录（本地 8138 端口）

```
301  /website/about.html                    → /about/index.html
301  /website/skill-hub.html                → /toolbox/skills.html
301  /website/workstation.html              → /toolbox/workstation.html
301  /website/ai-academy.html               → /learn/tutorials/index.html
301  /website/ai-academy/chapter-01.html    → /learn/tutorials/chapter-01.html
404  /website/nonexistent-xyz.html          （未知路径不跳转，正确）
```
