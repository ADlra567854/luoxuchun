## 一、为什么立这条规矩

老罗的原话：

> 「以后每次让你生成东西你都要……做个规划啥的，你都要写成文档的形式，搞一个完整的计划并严格执行」
> 「计划送进本地资料库及那个腾讯文档里面」
> 「去网上搜的材料也在知识库里面一一对应，并与你的资料库打通」

之前的问题是：规划只存在于对话里，做完就散。下次接手的是另一个会话，没有上下文，只能重头摸一遍。

**规矩一句话**：**先出文档，再动手；文档三端归档，做完回填结果。**

---

## 二、五步流程（每次任务必走）

| 步骤 | 动作 | 产物 | 落点 |
|---|---|---|---|
| ① 立计划 | 写完整计划文档 | `docs/PLANS/YYYY-MM-DD-<slug>.md` | 本地仓库 |
| ② 三端归档 | 同一份内容同步到资料库 + 腾讯文档 | 资料库文档节点 + 腾讯文档链接 | WorkBuddy 资料库 / 腾讯文档 |
| ③ 执行 | 严格按计划的步骤序列做，**不跳步、不临时改范围** | 代码/文件改动 | 项目目录 |
| ④ 验收 | 按计划里的「验收标准」逐条实测 | 验证输出 | 汇报正文 |
| ⑤ 回填 | 在计划文档末尾追加「执行结果」章节 | 计划文档本身 | `docs/PLANS/*.md` |

### 计划文档必含的章节

```markdown
# <任务名>

> 计划编号 · 立规日期 · 执行人 · 状态（进行中/已完成/已搁置）

## 0. 一句话目标
## 1. 背景与现状（含实测数据，不写估计值）
## 2. 目标与非目标
## 3. 执行步骤（有序，每步含：改哪个文件、怎么改、怎么验）
## 4. 验收标准（逐条可测，带具体数字）
## 5. 风险与回滚
## 6. 资源归档清单（资料库节点 / 腾讯文档 / 知识库条目）
## 7. 执行结果（完成后回填：实际改动、实测结果、遗留问题）
```

## 三、三端打通关系

```
        ┌─────────────────┐
        │  docs/PLANS/*.md │  ← 本地：唯一真源，可 git 版本化
        └────────┬────────┘
                 │ 同一份 Markdown
      ┌──────────┴──────────┐
      ▼                     ▼
┌───────────┐         ┌────────────┐
│ 资料库文档 │         │  腾讯文档   │
│ (library)  │         │ (tencent)  │
└─────┬─────┘         └────────────┘
      │ 一一对应（同编号、同标题、同正文）
      ▼
┌───────────┐
│  IMA 知识库 │  ← 网上搜来的材料入库，每条带来源链接
│  (ima-mcp) │
└───────────┘
```

**对应规则**：
- 计划文档 → 资料库文档节点 + 腾讯文档，标题统一用 `计划编号 · 任务名`
- 网上检索到的外部材料 → IMA 知识库条目，**每条必须在正文末尾写明原始来源 URL**
- 知识库条目命名带上计划编号（如 `2026-11-02-P01-xxx`），与资料库节点**编号一致**，形成一一对应
- 检索时先查资料库再查知识库，命中即引用编号

---

## 四、执行纪律

1. **不跳步**：计划里没有的动作不做。发现计划漏了 → 先改文档，再补做。
2. **不扩范围**：任务边界以计划第 2 节为准。想多做，先改计划并告知老罗。
3. **必实测**：验收标准里的每条都要有真实输出（数字、截图、HTTP 码），不接受「应该可以」。
4. **数据不编**：内容类数据（星数、价格、版本号、日期）必须来自可点开的出处。找不到就不写。
5. **诚实回报**：失败就写失败并说明卡在哪，不粉饰。
