持续集成与持续部署（CI/CD）指南

面向工科实训实验室：仿真代码、G 代码、静态网站，都可以做到「提交即自动测试、自动部署」。 配套工作流文件：github-actions-ci.yml（复制到仓库 .github/workflows/ci.yml 即可用）。

一、什么是 CI/CD（先讲人话）

CI/CD 是一套「让机器替你把重复劳动自动化」的工程方法。核心思想一句话：

代码一提交（push），服务器就自动帮你「集成测试 + 打包发布」，人在旁边看着结果就行。

它由三个词组成，很多人混为一谈，其实含义不同：

名词 英文 通俗解释 一句话
持续集成 Continuous Integration (CI) 每个开发者提交的代码，都自动合并到主干，并自动跑一遍测试，第一时间发现「你改的代码把别人的搞坏了」 提交 自动测试
持续交付 Continuous Delivery (CD) 在 CI 通过的基础上，自动把代码打包成可发布的版本，但「发布」这一步由人手动点一下 提交 测试 打包，人决定何时上线
持续部署 Continuous Deployment (CD) 比持续交付更进一步：测试通过后连上线也全自动，不需要人点 提交 测试 自动上线

记忆口诀：

  • CI 管「对不对」：自动测试，防止代码坏掉。
  • 持续交付管「能不能发」：自动打包，人手点发布。
  • 持续部署管「自动发」：连上线都全自动。

为什么「持续交付」和「持续部署」英文都缩写为 CD？因为它们都包含「自动把可交付产物准备好」这一步，差别只在「最终上线要不要人点」——这也是面试高频考点。

一个流水线（Pipeline）的典型样子：

push 代码
   │
   
[持续集成] 拉代码  装依赖  跑测试（pytest）
   │                      │ 失败  通知你，阻止合并
   │                      
   │                   测试通过
   
[持续交付/部署] 构建  打包  部署到服务器 / 静态托管

二、为什么仿真/代码也要上 CI

很多同学觉得「我就一个仿真脚本，自己本地跑跑不就行了，上 CI 干嘛？」——恰恰相反，越是要反复改的代码，越值得上 CI。原因：

  1. 防止「改坏了没发现」：仿真代码改个参数、改个公式，本地忘了跑测试就提交，CI 会立刻拦住你。
  2. 用「理论值」自动校验仿真对不对：本项目的 test_simulation.py 就是干这个的——它用物理公式的理论值（抛体射程、RC 时间常数、蒙特卡洛 π）去和仿真结果比对，误差超阈值就报错。这就是「仿真测试」的价值：让公式来当裁判。
  3. 环境一致性：别人电脑上「能跑」，你电脑上「跑不动」？CI 用一台干净、标准的环境（Python 3.12）重跑一遍，暴露「漏了依赖 / 写死了本机路径」这类问题。
  4. 自动化是工程素养：工科生未来进实验室、进企业，代码评审、回归测试、自动发布都是标配。现在就练会，简历上多一条硬通货。
  5. 免费且省心：GitHub Actions 对公开仓库免费，每次提交自动跑，不用自己买服务器。

一句话：CI 让你的代码「每次提交都有个机器替你兜底」。

三、GitHub Actions 入门

GitHub Actions 是 GitHub 自带的免费 CI/CD 服务，用 YAML 文件描述「什么时候、干什么」。

3.1 workflow 文件放在哪

工作流文件必须放在仓库的 .github/workflows/ 目录下，文件名任意，后缀 .yml，例如 .github/workflows/ci.yml。GitHub 会自动识别并执行。

3.2 整体结构（记住这四层）

name: 工作流名字                    # 第一层：名字（显示在 Actions 页）
on:                                 # 第二层：何时触发（trigger）
  push:
    branches: [ main ]
jobs:                               # 第三层：要干的任务们
  任务A:                            # 第四层：每个任务里的具体步骤
    runs-on: ubuntu-latest
    steps:
      - name: 步骤1
        run: echo "你好"

一个 YAML 文件 = 多个 job，一个 job = 多个 step，按顺序执行。缩进（空格）必须严格对齐，否则语法报错。

3.3 on —— 触发时机（trigger）

决定「什么动作会让流水线跑起来」：

触发词 含义 例子
push 推代码到分支 push: branches: [main]
pull_request 开/更新 PR pull_request: branches: [main]
schedule 定时任务 cron: '0 2 * * *'（每天 2 点）
workflow_dispatch 手动在网页点按钮触发 便于自己手动跑一次
paths 只有某些路径变了才触发 paths: ['lab/**'] 省 CI 分钟数

3.4 jobs / steps —— 干什么

  • job：一组跑在同一台虚拟机上的任务，可并行或串行（用 needs 指定依赖）。
  • step：job 里的最小执行单元，两种写法：
    • run: 直接执行 shell 命令；
    • uses: 调用别人封装好的「Action」（如 actions/checkout 拉代码、actions/setup-python 装 Python）。

3.5 一个最小可运行的例子

name: 最小示例
on: push
jobs:
  hello:
    runs-on: ubuntu-latest
    steps:
      - name: 打印一句话
        run: echo "第一次 CI 成功！"

把它存成 .github/workflows/hello.yml 提交，GitHub 就会自动跑，Actions 页能看到绿色的 。

四、把「仿真测试」接入 CI（每次 push 自动跑 pytest）

本项目已有测试文件 lab/simulation/test_simulation.py，它用 pytest 校验三件事：

  • 抛体运动射程 ≈ 理论值 R = v0²·sin(2θ)/g
  • RC 电路时间常数 τ = RC
  • 蒙特卡洛估算的 π 接近真实值

目标：每次 git push，GitHub 自动在干净的 Python 3.12 环境里跑 pytest。

完整步骤（和本目录的 github-actions-ci.yml 一致）：

  1. 在仓库根目录新建 .github/workflows/ci.yml，内容复制本目录的 github-actions-ci.yml。
  2. 在 lab/ 下放一个 requirements.txt（内容就是一行 pytest），供依赖缓存使用。
  3. 提交并推送：
git add .github/workflows/ci.yml lab/requirements.txt
git commit -m "ci: 接入仿真测试（每次 push 自动跑 pytest）"
git push
  1. 打开 GitHub 仓库 Actions 标签页，就能看到流水线实时运行；绿色 表示 4 条测试全部通过。

本地先验证（养成习惯，先本地跑通再上 CI）：

cd lab/simulation
pip install pytest          # 若还没装
pytest test_simulation.py -v # 应显示 4 passed

关键点：测试里用 importlib 通过 __file__ 定位同目录的仿真脚本（03_projectile.py 等），所以无论从哪个目录运行 pytest，都能正确加载，CI 里无需额外配置路径。

五、自动部署静态网站

本项目的 website/ 目录是纯静态 HTML/CSS（无需构建），可以零成本部署到 GitHub Pages 或 Vercel，实现「改一页 push 网站自动更新」。

方案 A：GitHub Pages（官方、免费、无需第三方账号）

原理：用两个官方 Action 把 website/ 目录打包成「Pages 产物」并发布。

前置：仓库 Settings Pages Build and deployment Source 选 GitHub Actions（只设置一次）。

# .github/workflows/deploy-pages.yml
name: 部署网站到 GitHub Pages
on:
  push:
    branches: [ main ]
    paths:
      - 'website/**'          # 只有网站内容变化才部署
# Pages 部署需要额外权限
permissions:
  contents: read
  pages: write
  id-token: write
# 同一时间只跑一个部署，避免并发冲突
concurrency:
  group: pages
  cancel-in-progress: true
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: 检出代码
        uses: actions/checkout@v4
      - name: 打包 website 目录
        uses: actions/upload-pages-artifact@v3
        with:
          path: website          # 关键：只发布 website/ 子目录
  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deploy.outputs.page_url }}
    steps:
      - name: 部署到 Pages
        id: deploy
        uses: actions/deploy-pages@v4

部署后：网站地址为 https://<你的用户名>.github.io/<仓库名>/。注意 website/index.html 里的相对链接（如 ../lab/...）在 Pages 根路径下可能变化，如有需要可在 Pages 的 Settings 里配置 Custom domain。

方案 B：Vercel（更快、最省事、自带 CDN）

方式一（推荐，零配置）：直接去 vercel.com 用 GitHub 登录 Import 仓库 Root Directory 填 website Deploy。之后每次 push 到 main 都自动部署，还会为每个 PR 生成预览链接。

方式二（用 GitHub Actions 控制）：

  1. 在 Vercel 项目 Settings 里拿到 VERCEL_ORG_ID、VERCEL_PROJECT_ID，并生成 VERCEL_TOKEN。
  2. 把三者存进 GitHub 仓库的 Secrets。
  3. 写工作流：
# .github/workflows/deploy-vercel.yml
name: 部署网站到 Vercel
on:
  push:
    branches: [ main ]
    paths:
      - 'website/**'
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: 检出代码
        uses: actions/checkout@v4
      - name: 部署到 Vercel（生产环境）
        uses: amondnet/vercel-action@v25
        with:
          vercel-token: ${{ secrets.VERCEL_TOKEN }}
          vercel-org-id: ${{ secrets.VERCEL_ORG_ID }}
          vercel-project-id: ${{ secrets.VERCEL_PROJECT_ID }}
          vercel-args: '--prod'
          working-directory: website

选型建议：纯静态网站，GitHub Pages 最省事（全 GitHub 生态、免费）；需要自定义域名、全球 CDN、PR 预览链接，用 Vercel 体验更好。

六、常见坑

  1. YAML 缩进错误：YAML 靠空格缩进划分层级，不能用 Tab，统一用 2 或 4 个空格。on、jobs 顶格，steps 缩进 6 格等，层级错一个空格就报 mapping values are not allowed here。
  2. on: push 触发不了：确认工作流在默认分支上、且路径是 .github/workflows/*.yml；paths 写太窄也会导致「改的文件不在名单里，永远不触发」。
  3. cache: 'pip' 报「找不到依赖文件」：setup-python 需要 cache-dependency-path 指向真实存在的文件（本项目指向 lab/requirements.txt）。文件不存在时只是不缓存并告警，不会让任务失败。
  4. 测试「本地能过、CI 上挂」：多半是路径写死或漏装依赖。CI 是干净环境，任何 import 没声明在依赖里就会挂。原则：测试里一律用 __file__ 定位文件，别写绝对路径。
  5. actions/checkout 版本太老：GitHub 已要求 Node20+ 的 Action，旧版 checkout@v2 可能报 deprecated；用 v4 / v5 等新版本。
  6. Pages 部署 404：先确认 Settings Pages Source 选了 GitHub Actions；其次确认 upload-pages-artifact 的 path 指向正确（本项目是 website，不是仓库根）。
  7. 权限不足：Pages 部署需 permissions: pages: write 和 id-token: write，少了会报 403。
  8. 密钥（Secret）写进代码：Webhook 地址、Vercel Token 等一律放 GitHub Secrets，用 ${{ secrets.XXX }} 引用，绝不硬编码到 yaml（否则会被扫出来泄露）。
  9. curl 通知在 Windows 环境不可用：本工作流用 ubuntu-latest，自带 curl；若换 windows-latest 需改用 PowerShell。
  10. 改工作流本身也要触发：paths 里记得包含 .github/workflows/**，否则改了工作流文件自己却不跑，容易误判。

七、可复制命令速查

# 1. 本地先跑通测试（上 CI 前必做）
cd lab/simulation
pip install pytest
pytest test_simulation.py -v            # 期望 4 passed
# 2. 接入 CI：复制工作流文件到仓库
#    把 lab/cicd/github-actions-ci.yml 复制为 .github/workflows/ci.yml
cp lab/cicd/github-actions-ci.yml .github/workflows/ci.yml   # 或手动创建
# 3. 提交并触发
git add .github/workflows/ci.yml lab/requirements.txt
git commit -m "ci: 每次 push 自动跑仿真测试"
git push
# 4. 看结果：GitHub 仓库  Actions 标签页
