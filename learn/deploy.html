部署百科 · 先选路线，再选引擎

自建推理最常见的错误是顺序搞反：先挑一个「性能最强」的引擎，装到一半发现显卡装不下、或者服务端跑得好但自己只是单人用。正确顺序是先定路线（本地 / 云 / 自建服务），再定引擎。这一页按这个顺序写。

第一步 · 选路线

四种路线覆盖 95% 的需求，按人群分

命令行派 · Ollama

开发者 / 技术爱好者
最省事

一行命令跑起来，模型库覆盖 100+ 模型，默认开 OpenAI 兼容接口（11434）。适合把本地模型接进自己的脚本与工具链。

难度 1免费国内可直连

图形界面派 · LM Studio

非技术用户
零门槛

可视化下载模型、性能测试、开 API 服务。不用碰命令行，代价是安装包大、扩展性不如 Ollama。

难度 1个人免费国内可直连

云端免费派

不想装任何东西
零硬件

阿里云百炼、硅基流动、智谱、混元都有新用户额度，国内直连快。缺点有限速与「仅实时推理」约束，数据要过第三方。

难度 0免费额度国内可直连

企业级路线 · vLLM / SGLang

IT / MLOps
要运维

高并发、多卡、可观测。需要 GPU 服务器与运维能力，个人用不上，团队上线必备。

难度 3需要 GPU国内可直连

第二步 · 按条件走决策树

从上往下读，第一条命中的就是答案，不用全部比较
  • 完全没有 GPU，只有 CPU纯 CPU 或老笔记本
    →
    llama.cpp 直接跑唯一认真对待 CPU 的引擎，AVX2/NEON 都有优化
  • Apple Silicon 笔记本MacBook / Mac mini
    →
    Ollama 或 LM StudioMLX 走后端，比纯 CPU 快数倍，安装零门槛
  • 一张消费级显卡，单人用RTX 4060 / 4090
    →
    Ollama 起步，需要调参再换 llama.cpp单用户场景 vLLM 的并发优势用不上
  • 3–10 人共享一台 GPU 工作站团队内部工具
    →
    LM Studio 远端 / Ollama 加反代不用运维整套服务，性能够用
  • 生产服务，5 并发以上A100 / H100 单机
    →
    vLLM连续批处理真正开始回本，运维成本可接受
  • 多机多卡、多租户集群
    →
    vLLM 或 SGLang张量并行 + PagedAttention 是生产标准
  • RAG / Agent，前缀高度重复长 system prompt、多轮
    →
    SGLang 优先，其次 vLLMRadixAttention 的前缀缓存在这个形状下优势最大
  • 模型装不进一张卡显存不够
    →
    llama.cpp --tensor-split / vLLM 张量并行单用户拆卡用前者，对外服务用后者

引擎横评

6 个引擎
吞吐量为 2026 年公开评测数据（A100/H100 上测 70B 级模型；llama.cpp 一行为 7B 模型单机 CPU/Metal 测试，与 GPU 数据不可直接比较）。
引擎出品方吞吐 token/s上手难度什么时候选它
vLLMVLM 团队1000–2000中等生产级高并发默认选择。PagedAttention 做显存分页复用，连续批处理把吞吐拉满。5 并发以上就该换它。
TensorRT-LLMNVIDIA2500–4000+困难吞吐天花板，但要针对显卡型号编译引擎，换卡就要重编。有专职工程团队才值得上。
SGLangLMSYS / Berkeley很高（前缀命中时领先）中等RadixAttention 复用前缀 KV 缓存。system prompt 长、多轮、RAG 场景优势明显；每个请求都不同时优势消失。
TGIHugging Face800–1500中等企业级部署的老方案，2025 年 12 月起进入维护模式，只修 bug 不加功能。新项目不建议再选。
llama.cppggml-org80–100（7B / M2 Ultra，CPU+Metal）中等唯一把纯 CPU 推理当一等公民的引擎，GGUF 格式的定义者。边缘设备与离线场景无可替代。
OllamaOllama较低（多请求时吞吐见顶）极低一行命令起步，底层是 llama.cpp。开发原型与单用户的最佳选择，不是服务端方案。
吞吐量不是唯一指标。vLLM 在高并发下最强，但单用户低延迟场景可能不如别的；llama.cpp 的绝对数字低，却是 CPU 和边缘设备上唯一现实的选择。先定场景，再看数字。

第三步 · 算硬件够不够

显存 + 内存是唯一需要关心的两个数字
「显存 + 内存」指量化后可装入的总容量，不是模型原始体积。32 GB 内存已成为 2026 年的入门基线。
模型规模量化后占用推荐配置能干什么
1B – 3B1 – 2 GB任何近五年的电脑轻量对话、输入法补全、端侧分类
7B – 8B4 – 6 GB8 GB 内存 + 核显即可日常对话、写作辅助、简单 RAG
13B – 14B8 – 10 GB16 GB 内存 + 独显复杂推理、长文本摘要、代码补全
32B – 34B18 – 22 GB32 GB 内存 + 中高端独显（24G 卡）高级推理、成规模的代码生成
70B+40 GB+48 GB+ 内存 + 高端独显或多卡专业任务、接近云端水平的通用能力

第四步 · 选量化格式

Q4_K_M 是绝大多数人的答案
格式位宽压缩率质量适用建议
Q2_K2 bit极高较差只考内存极度受限时不推荐
Q3_K_M3 bit高一般空间紧张且能接受质量下降勉强
Q4_K_M4 bit中高良好绝大多数场景推荐
Q5_K_M5 bit中较好质量要求高于速度可选
Q8_08 bit低接近原始对速度不敏感但要求质量高配
FP1616 bit无原始专业级、不计资源基准

量化就是把 16 位浮点参数压成 4–8 位整数。Q4_K_M 把体积压到原来的约四分之一，同时保住九成以上能力，所以成了默认推荐。 觉得质量不够再升 Q5 或 Q8，不要一上来就用 Q2 —— 省下的那点内存换来的质量下降通常不值。

第五步 · 跑起来

三条命令覆盖三种典型场景

场景 A · 本地先跑通（Ollama）

# 安装（Windows 直接下安装包，Linux 用这行） curl -fsSL https://ollama.com/install.sh | sh # 拉一个 8B 量化模型并对话 ollama run qwen3:8b # 它同时在 11434 开了 OpenAI 兼容接口，任何框架都能直接接 curl http://localhost:11434/v1/chat/completions \ -H "Content-Type: application/json" \ -d '{"model":"qwen3:8b","messages":[{"role":"user","content":"你好"}]}'

场景 B · 团队共享一台 GPU（vLLM）

# 装 vLLM（需要 CUDA 环境） pip install vllm # 起一个 OpenAI 兼容服务：吞吐按显存比例分配，0.9 是常用值 vllm serve Qwen/Qwen3-8B \ --gpu-memory-utilization 0.90 \ --max-model-len 32768 \ --port 8000 # 客户端只改 base_url，其余代码不用动 curl http://localhost:8000/v1/chat/completions ...

场景 C · 没有显卡，纯 CPU 硬跑（llama.cpp）

# 从 HuggingFace 下 GGUF（注意选 Q4_K_M） huggingface-cli download Qwen/Qwen3-8B-GGUF qwen3-8b-q4_k_m.gguf # 起一个带网页界面的本地服务，--n-gpu-layers 0 表示纯 CPU ./llama-server -m qwen3-8b-q4_k_m.gguf \ -c 4096 --n-gpu-layers 0 --port 8080

踩坑清单

这些错误每周都有人在犯
① 用 Ollama 上生产。单人用没问题；5 并发以上吞吐会突然见顶，而且不是调参能救的——那是工具选错了，不是配置问题。

② 显存刚好够就以为能跑。KV cache 会随上下文长度线性增长。8G 卡装 7B 时，把 --max-model-len 设成 32k 大概率 OOM。

③ 下 GGUF 不看来源。llama.cpp 的 GGUF 解析器在 2026 年 5 月被披露过 6 个未编号 CVE 的漏洞，恶意文件在推理开始前就能触发。只从可信仓库下载。

④ 忽略模型许可证。开放权重不等于可商用。Llama 系列有命名与用户数条款，部分中文模型禁止特定用途。上线前读一遍。

⑤ 忘了算电费与时间。本地跑不花 token 钱，但一张 4090 满载是 450W。真正的成本对比要把硬件折旧、电费、以及你调环境的两天一起算进去。
