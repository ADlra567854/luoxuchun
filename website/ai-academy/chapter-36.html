微软 Orchard 框架：Agent 训练基础设施与数据蒸馏实战

本章将系统拆解微软研究院2026年开源的Orchard Agent训练框架，覆盖其K8s原生沙箱架构、三类官方训练配方、数据蒸馏核心技术与落地路径，学完你将能够独立搭建Agent训练的沙箱基础设施，复用开源轨迹数据完成SFT/RL全流程训练，用3B级小模型逼近大模型Agent的SWE-bench基准表现。

Orchard框架基础定位与官方信息

Orchard是微软研究院于2026年7月正式开源的Agentic AI建模基础设施，项目托管于GitHub microsoft/Orchard仓库，采用MIT开源协议，对应学术论文预印本为arXiv:2605.15040，官方技术说明发布于微软研究院博客microsoft.com/en-us/research/blog/orchard-an-open-framework-for-scalable-agentic-ai/，所有功能与性能参数请以官方最新发布文档为准。与同期多数Agent应用框架不同，Orchard的初始版本就定位为训练侧基础设施，而非面向终端用户的Agent编码助手或工作流编排工具。

Orchard核心解决的是Agent开发团队的重复造轮子问题：几乎所有团队构建生产级Agent时，都需要从零实现沙箱生命周期管理、多轮轨迹数据蒸馏、RL rollout调度、评估基准对接这四类通用脚手架，Orchard将这些能力抽象为统一的底层服务，上层可以对接任意Agent运行时与编排框架。它与本教程其他章节的框架是明确互补关系：

  • 与第25章LangGraph：LangGraph负责Agent的工作流编排与节点逻辑定义，Orchard为LangGraph提供可弹性扩缩的沙箱执行环境与训练数据生成管道
  • 与第28章DeepSeek Harness：DeepSeek Harness是Agent运行时的执行层实现，Orchard为其提供统一的环境抽象、rollout调度与奖励信号计算能力
  • 与第34章NOOA对象导向Agent：NOOA定义了Agent的对象交互范式与记忆结构，Orchard为其提供训练阶段的轨迹收集、蒸馏与RL优化基础设施

你可以通过执行git clone https://github.com/microsoft/Orchard.git && cd Orchard && cat README.md命令验证仓库开源协议与基础定位说明。

核心架构：K8s原生的低延迟沙箱服务

Orchard的核心组件是Orchard Env，这是一套Kubernetes原生的沙箱管理服务，它将沙箱的创建/销毁、命令执行、文件读写、网络策略管控四类高频操作抽象为统一的REST API，上层应用不需要直接感知K8s的Pod、Service、NetworkPolicy等底层资源。整个控制面采用FastAPI编写Orchestrator模块负责资源调度，Python SDK封装了所有环境操作接口，默认支持CPU/GPU混合资源调度、沙箱资源配额限制、多租户隔离等生产级特性。

为了降低Agent多轮交互的执行延迟，Orchard采用了数据面与控制面分离的设计：沙箱创建、权限配置等管控类请求走K8s API Server完成调度，而命令执行、文件读写等高频数据面请求会绕过API Server，通过gRPC直连目标沙箱Pod的sidecar代理，端到端执行延迟比传统K8s exec方式明显降低（幅度随实现与数据而变，需自测）。同时Orchard采用harness无关设计，同一套基础设施可以无差别支持三类核心场景：监督微调（SFT）的轨迹数据收集、强化学习（RL）的rollout采样、训练完成后的最终效果评估，不需要为不同阶段搭建独立的环境集群。

Orchard Env的核心API接口列表如下：

接口路径方法功能说明
/api/v1/sandboxesPOST创建指定配置的沙箱实例，支持指定镜像、资源配额、网络权限
/api/v1/sandboxes/{id}/execPOST在目标沙箱内执行Shell命令，返回实时stdout/stderr
/api/v1/sandboxes/{id}/filesPUT/GET向沙箱内上传/下载文件，支持目录递归操作
/api/v1/sandboxes/{id}DELETE销毁沙箱并释放所有关联资源

你可以通过查看Orchard仓库orchard/env/目录下的FastAPI路由定义验证上述接口设计。

三类官方训练Recipe与基准表现

Orchard官方开源了三个覆盖主流Agent场景的训练配方，所有配方均提供完整的训练脚本、数据处理管道与基准评估代码，性能指标均来自官方公开测试结果，请以官方文档为准。第一个是Orchard-SWE软件工程配方，这是目前完成度最高的配方：采用约3B活跃参数的小模型架构，训练轨迹覆盖2788个真实GitHub仓库的Issue修复任务，轨迹由MiniMax-M2.5与Qwen3.5-397B两个前沿大模型生成，同时支持OpenHands与mini-swe-agent两种主流SWE Agent harness，在SWE-bench Verified基准上达到73%的解决率，追平同期闭源前沿模型的表现。

第二个是Orchard-GUI浏览器导航配方，针对网页操作类视觉Agent设计，采用4B参数的视觉语言模型架构，训练数据覆盖WebVoyager、Online-Mind2Web、DeepShop三个主流GUI Agent基准的任务场景，支持浏览器沙箱的视觉截图、DOM树获取、鼠标键盘动作模拟三类核心交互，目前为概念验证版本。第三个是Orchard-Claw个人助手配方，面向跨应用个人助理场景，配套Claw-Eval专属评估基准，覆盖邮件处理、日程安排、文档编辑三类常见个人任务，目前仅开源了基础框架与评估脚本。

三类配方的核心参数对比如下：

配方名称目标场景模型规模支持harness对应基准
Orchard-SWE软件工程Issue修复3B活跃参数OpenHands/mini-swe-agentSWE-bench Verified
Orchard-GUI浏览器导航操作4B VLMBrowserEnvWebVoyager/Online-Mind2Web/DeepShop
Orchard-Claw跨应用个人助手7B多模态DesktopEnvClaw-Eval

你可以通过查看Orchard仓库recipes/目录下的配置文件验证各配方的参数设置。

关键技术：从轨迹蒸馏到RL的递进提升路径

Orchard-SWE配方的性能提升采用了三步递进的技术路线，官方公开的SWE-bench Verified基准分数从基线的61.4%逐步提升到73.0%，所有技术细节均在论文中公开。第一步是Balanced Adaptive Rollout（BAR，平衡自适应采样）机制，该机制会根据任务难度动态调整采样的轨迹数量：对于简单任务减少大模型采样次数以降低数据生成成本，对于复杂任务增加采样次数直到获得至少一条成功轨迹，相比固定采样次数的方案，数据生成成本明显降低（幅度随实现与数据而变，需自测）的同时轨迹多样性明显提升（幅度随实现与数据而变，需自测）。

第二步是on-policy蒸馏结合基于评分规则的过程奖励（rubric-based process reward）：不同于传统SFT只使用最终成功的轨迹做蒸馏，Orchard会为每一步操作设计细粒度的评分规则（比如是否成功读取目标文件、是否定位到错误代码行、是否通过单元测试），生成密集的过程奖励信号，即使是最终失败的轨迹，只要中间步骤符合评分规则也会被纳入训练集，这一步将模型性能从61.4%提升到69.1%。第三步是价值模型重排序（value-model reranking）：在推理阶段，模型会生成多个候选解决方案，用训练好的过程价值模型对候选方案打分，选择得分最高的方案提交，这一步带来0.6%的性能提升，最终结合失败轨迹挖掘技术达到73.0%的解决率。

关键技术对应的性能提升节点如下：

  • 基线（仅成功轨迹SFT）：61.4%
  • +BAR自适应采样：65.2%
  • +on-policy蒸馏+过程奖励：69.1%
  • +价值模型重排序：69.7%
  • +失败轨迹价值挖掘：73.0%

你可以通过查阅arXiv论文第4章的实验部分验证上述提升路径的细节。

失败轨迹的价值挖掘与数据资产

Orchard最具特色的设计是对失败轨迹的价值挖掘，官方提出的retrospective value estimation（回溯价值估计）方法，不需要依赖最终任务是否成功，而是通过过程奖励模型回溯每条失败轨迹，提取其中对解决问题有明确进展的片段（比如成功定位到Bug位置、写出了正确的修复逻辑但存在语法错误、通过了部分单元测试），将这些片段作为有效训练数据纳入SFT与RL训练集，大幅降低了对完美成功轨迹的依赖。

官方公开的Orchard-SWE数据集总共包含107,185条轨迹，其中仅74,649条是最终解决问题的成功轨迹，剩余32,536条是未解决问题的失败轨迹，经过回溯价值估计筛选后，失败轨迹中41%的步骤片段被标记为有效训练数据，这些片段将小模型的SWE-bench表现提升了3.3个百分点。除了SWE场景的轨迹，官方同时在HuggingFace上开源了3070条GUI场景的rollout轨迹，其中同样包含大量失败交互片段，可用于GUI Agent的训练。

Orchard的开源资产清单如下：

  • GitHub主仓库：包含Orchard Env环境服务代码、Python SDK、三个训练配方的完整训练与评估脚本
  • HuggingFace数据集：microsoft/orchard-swe-trajectories含10.7万条SWE轨迹，microsoft/orchard-gui-rollouts含3070条GUI轨迹
  • 配套OpenForge RL项目：支持在真实部署harness中完成Agent的RL训练，覆盖ZeroClaw、OpenClaw、Codex三类Agent运行时

你可以通过执行pip install datasets && datasets.load_dataset("microsoft/orchard-swe-trajectories", split="train")命令验证数据集的存在与规模。

安装部署与基础上手流程

Orchard的部署分为K8s集群侧的Orchard Env服务与客户端侧的Python SDK两部分，所有命令与配置参数请以官方安装文档为准。首先准备K8s环境：要求Kubernetes版本≥1.28，默认配置下需要至少4个CPU节点、16G可用内存、100G存储空间，如果需要运行GUI或SWE训练任务，需要额外配备GPU节点。部署Orchard Env可以直接使用官方提供的Helm Chart：

# 添加Orchard Helm仓库
helm repo add orchard https://microsoft.github.io/Orchard/helm-charts
helm repo update
# 在orchard命名空间部署Orchard Env服务
helm install orchard-env orchard/orchard-env --namespace orchard --create-namespace

客户端Python SDK安装与基础调用非常简洁，不需要直接操作K8s资源，只需要指定Orchard Env的服务地址即可完成沙箱创建、命令执行等操作：

# 安装Python SDK，要求Python版本≥3.10
pip install orchard-ai
from orchard import OrchardClient
# 初始化客户端，替换为你的Orchard Env服务地址
client = OrchardClient(base_url="http://orchard-env.orchard.svc.cluster.local:8000")
# 创建一个Ubuntu 22.04沙箱，限制1核CPU、2G内存，禁止公网访问
sandbox = client.create_sandbox(
    image="ubuntu:22.04",
    cpu_limit=1,
    memory_limit="2G",
    allow_network=False
)
# 在沙箱内执行命令，打印输出
result = sandbox.exec("echo 'Hello Orchard' && ls -la")
print(result.stdout)
# 销毁沙箱释放资源
sandbox.delete()

对于自定义harness的接入，只需要将原有harness中的本地命令执行、文件操作替换为Orchard SDK对应的接口，即可自动获得沙箱弹性调度、轨迹自动记录、奖励信号计算的能力，不需要修改harness的核心逻辑。你可以通过运行上述SDK示例代码，验证沙箱创建与命令执行功能是否正常。

适用场景与使用注意事项

Orchard主要面向三类用户群体：第一类是高校与企业研究院的Agent研究团队，可以基于Orchard的统一基础设施快速开展SFT、RL算法的迭代，不需要重复搭建沙箱与数据管道；第二类是中大型组织的Agent工程团队，可以复用Orchard的沙箱管理能力支撑内部多个Agent应用的数据收集、测试与上线前评估；第三类是小模型Agent创业团队，可以基于开源的10万+轨迹数据，用3B-7B级小模型训练出逼近千亿参数大模型的Agent能力，大幅降低推理成本。

但Orchard目前仍是研究级框架，存在明确的使用门槛与局限：首先是运维门槛较高，Orchard Env依赖Kubernetes集群，需要专业的运维人员完成集群部署、网络配置、资源调度与故障排查，不适合个人开发者在本地单机环境完整运行；其次是目前Orchard-GUI与Orchard-Claw两个配方的开源数据量较薄，属于概念验证版本，距离生产级可用还有差距；最后是SWE配方的全流程训练对硬件要求较高，官方训练成本与硬件配置要求请以文档为准，个人开发者建议直接基于开源轨迹做微调或者直接使用开源的模型权重。

不适合使用Orchard的场景包括：个人开发者本地调试简单Agent Demo、不需要训练仅做Agent工作流编排、没有K8s运维能力的小型团队，这些场景下直接使用LangChain、AutoGPT等轻量框架的成本更低。你可以通过查看Orchard官方文档的Requirements章节，确认自身环境是否满足部署要求。

小结与练习

核心收获

  1. Orchard是微软开源的Agent训练基础设施，定位为沙箱管理、数据蒸馏、RL rollout的统一底层，与LangGraph、DeepSeek Harness等编排/运行时框架互补，而非直接竞争
  2. Orchard采用K8s原生架构实现低延迟沙箱管理，通过BAR自适应采样、过程奖励蒸馏、价值模型重排序、失败轨迹挖掘四类核心技术，实现3B小模型在SWE-bench Verified上73%的解决率
  3. Orchard开源了完整的环境代码、训练脚本与10万+条包含失败片段的轨迹数据，支持任意harness接入，可大幅降低Agent训练的基础设施搭建成本

动手练习

  1. 本地安装Orchard Python SDK，连接公开测试沙箱服务（地址见官方文档），完成沙箱创建、文件上传、命令执行、沙箱销毁的完整流程
  2. 从HuggingFace加载100条Orchard-SWE的失败轨迹，统计其中“成功定位到错误文件”的有效步骤占比，验证失败轨迹的价值
  3. 参考官方示例，将mini-swe-agent的本地执行层替换为Orchard SDK，跑通一个SWE-bench任务的rollout采样

扩展阅读方向

阅读配套OpenForge RL项目的文档，尝试理解在真实harness环境中做Agent在线RL训练的技术难点，对比传统离线RL与在线RL在Agent训练场景下的效果差异。
